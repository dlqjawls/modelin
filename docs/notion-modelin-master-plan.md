# Modelin — 멀티마켓 퀀트 자동매매 개발 계획

> 국장·미장·코인을 대상으로 전략 수립, 백테스트, 모의투자, 자동 주문, 체결·잔고 복구까지 하나의 시스템으로 구축한다.

## 현재 상태

**단계:** 상세 설계 완료 → 1차 구현 준비  
**최종 목표:** 시장별 데이터를 수집하고 검증된 전략에 따라 자동으로 매수·매도하며, 주문·체결·잔고를 장애 이후에도 정확히 복구하는 개인용 퀀트 투자 프로그램  
**실거래 연결:** 국내·미국 증권사 및 코인 거래소 미정  
**1차 범위:** 현물 롱·현금, 일봉, 개인 계좌, 백테스트·모의투자 우선

## 제품 원칙

- 백테스트, 모의투자, 실거래가 같은 전략 판단과 위험 검사 코드를 사용한다.
- 국장·미장·코인의 차이는 시장 데이터와 브로커 어댑터에 둔다.
- 전략은 주문을 직접 보내지 않고 목표 비중과 판단 근거만 반환한다.
- 주문·체결·현금·수량은 원장에 기록하며 `Decimal`로 계산한다.
- 브라우저가 닫히거나 서버가 재시작돼도 워커가 상태를 복구한다.
- 실거래는 모의투자 검증 이후 별도 계좌·별도 배포로 활성화한다.
- 계좌 사이의 자동 이체·환전은 1차 범위에서 제외한다.
- 공매도·신용·선물·레버리지·초단타는 후속 범위로 둔다.

### 확인된 핵심 문제

1. 당일 종가로 계산한 신호를 같은 날 수익률에 적용해 미래 정보가 섞인다.
2. 신호 `0`을 홀드로 설명하지만 실제 계산에서는 미보유로 처리한다.
3. 최초 매수 비용이 누락되고, 다종목 비용이 실제 비중과 다르게 계산된다.
4. `rebalance_period`를 받아도 실행에서 사용하지 않는다.
5. 잘못된 전략 이름을 오류로 처리하지 않고 동일가중으로 실행한다.
6. 국장은 최대 150개 후보 중 앞 100개만 스크리닝하여 KOSDAQ가 제외될 수 있다.
7. 미장은 고정 50개 목록이고 기본 시가총액이 0이라 전체시장 스크리닝이 아니다.
8. 코인은 재무 데이터가 비어 있어 주식용 조건을 공통 적용할 수 없다.
9. 주문 상태, 부분체결, 중복 방지, 잔고 대사, 재시작 복구가 없다.

## 목표 아키텍처

```text
React 운영 화면
    ↓
FastAPI 제어 API ── PostgreSQL
    ↓                    ↑
독립 운용 워커 → 시장 데이터 검증
    ↓
공통 전략 판단 → 목표 비중
    ↓
자금 배분 → 위험 검사 → 주문 계획
    ↓
주문 의도 저장 → 브로커 어댑터
    ↓
백테스트 체결 / 모의 브로커 / 실거래 브로커
    ↓
체결 이벤트 → 원장 → 잔고 대사 → 다음 판단
```

### 코드 모듈

- `domain`: 전략 판단, 자금 배분, 위험 검사, 주문 계획, 회계 계산
- `application`: 전략 실행, 주문 발송, 체결 반영, 잔고 대사, 배포 제어
- `ports`: 시장 데이터, 브로커, 저장소, 시계의 공통 계약
- `adapters`: 국장·미장·코인 데이터 및 모의·실거래 연결
- `backtesting`: 과거 이벤트 재생, 체결 모델, 성과 계산
- `workers`: 전략 실행, 주문 전송, 체결 수집, 백테스트 작업
- `api`: 계좌·전략·백테스트·운용 제어 API

## 전략과 실행 규칙

전략 결과는 `1/0/-1` 대신 아래 세 종류로 표현한다.

- `NO_CHANGE`: 현재 목표와 주문을 유지한다.
- `TARGET`: 전체 대상 자산의 목표 비중을 새로 제시한다. 빈 목표는 전량 현금이다.
- `BLOCKED`: 데이터 부족이나 상태 이상으로 주문을 만들지 않는다.

판단 시점까지 완성되어 공개된 데이터만 사용한다. 일봉 기반 1차 백테스트는 **종가 확정 후 판단 → 다음 거래 가능한 시가에 체결**을 기본으로 한다. 동일 신호가 유지되면 보유 수량을 고정하고, 신호 변경 또는 정기 리밸런싱 때만 거래한다.

초기 전략은 동일가중, 이동평균, RSI, 볼린저, 가격 모멘텀부터 구현한다. 팩터 전략은 과거 시점의 종목·재무 데이터가 준비된 이후 추가한다.

## 주문과 장애 처리

주문은 `CREATED → SUBMITTING → OPEN → PARTIALLY_FILLED → FILLED` 흐름을 기본으로 하고, `REJECTED`, `CANCELED`, `EXPIRED`를 분기한다. 네트워크 전송 결과를 모르면 `UNKNOWN`으로 두고 조회하여 해소한다.

- 같은 일정의 전략 실행은 `run_id`와 DB 유니크 제약으로 하나만 생성한다.
- 동일 체결 이벤트는 한 번만 원장에 반영한다.
- 부분체결은 체결된 수량만 반영하고 잔여 예약금을 유지한다.
- 취소 요청만으로 예약금을 풀지 않고 취소 확정을 확인한다.
- 주문 접수 여부가 불명확하면 확인 전 신규 노출을 막는다.
- 재시작 시 주문보다 잔고·미체결·최근 체결 대사를 먼저 수행한다.
- 중지는 `PAUSE`, `CANCEL_OPEN`, `LIQUIDATE`로 구분한다.

## 필요한 데이터 모델

- Instruments / Instrument Rules: 거래 장소, 통화, 심볼 이력, 가격·수량 단위, 최소 주문금액
- Bars / Corporate Actions / Fundamental Versions: 시간대가 있는 봉, 분할·배당, 공시·정정 이력
- Strategy Versions / Deployments / Strategy Runs: 불변 전략 버전, 계좌 배포, 판단 기록
- Accounts / Cash / Allocations: 계좌별 통화, 가용·예약 현금, 전략 배정액
- Order Intents / Orders / Order Events / Fills: 주문 계획, 외부 주문, 상태 변화, 개별 체결
- Journals / Positions / Account Snapshots: 원장 원본, 조회용 보유, 외부 잔고 스냅샷
- Reconciliations / Risk Events / Worker Heartbeats / Outbox: 대사, 중지 사유, 워커 상태, 재전송 작업
- Backtest Jobs / Results: 비동기 계산, 데이터·전략·비용 버전이 고정된 결과

## API 목표

- `POST /api/v1/accounts/paper` — 모의 계좌 생성
- `POST /api/v1/strategies` — 전략 버전 생성
- `POST /api/v1/backtests` — 백테스트 작업 생성
- `POST /api/v1/deployments` — 전략과 계좌 연결
- `POST /api/v1/deployments/{id}/commands` — 시작·중지·취소·청산
- `GET /api/v1/accounts/{id}/snapshot` — 현금·예약금·포지션 조회
- `GET /api/v1/accounts/{id}/orders` — 주문과 부분체결 조회
- `GET /api/v1/deployments/{id}/runs` — 전략 판단과 근거 조회
- `GET /api/v1/capabilities` — 시장·전략·주문 지원 범위 조회

## 출시 판단 기준

실거래 전 아래 항목을 자동 테스트와 모의 환경에서 확인한다.

- 미래 데이터를 바꾸어도 과거 판단이 변하지 않는다.
- 첫 매수·매도·리밸런싱에 실제 거래비용이 반영된다.
- 동일 체결이 두 번 와도 현금과 수량은 한 번만 변한다.
- 주문 접수 직후 통신이 끊겨도 중복 주문이 발생하지 않는다.
- 부분체결 중 취소해도 실제 체결 수량과 예약금이 일치한다.
- 워커 두 개가 동시에 실행돼도 같은 주문은 하나만 생성된다.
- 프로세스를 재시작하면 잔고 대사 후 안전하게 재개한다.
- 오래된 시세, 휴장, 거래정지, 현금 부족은 주문을 차단하고 원인을 표시한다.
- Paper 계좌가 Live 어댑터를 호출하지 못한다.
- API 사용자와 계좌 소유권이 모든 조회·명령에서 검증된다.
