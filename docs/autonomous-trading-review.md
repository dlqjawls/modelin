# Modelin 자동 운용 목표 대비 코드 검토

검토일: 2026-09-11. 현재 작업 트리 기준. 증권사·거래소는 사용자 답변에 따라 미정.

## 결론과 범위

목표는 국장·미장·코인에서 전략에 따라 종목을 선정하고 매수·매도하며 지속적으로 운용하는 프로그램이다. 현재 구현은 시세 조회, 차트, 스크리닝, 이벤트 기반 백테스트, paper 전략 실행, 주문 원장, KIS 국내주식 paper 어댑터까지 포함한다. 해외주식 주문 어댑터와 코인은 보류하며 live 어댑터는 안전상 등록하지 않는다.

이번 검토는 로컬 코드, 합성 데이터 계산 재현, 프론트엔드 빌드를 대상으로 했다. 실계좌·외부 DB·시세 API의 실제 연결은 검증하지 않았다. 소스 로직 수정이나 주문 실행은 하지 않았다. 기존 backend/config.py 수정은 유지했다.

초기 설계 범위는 개인 계좌, 현물 매수·매도, 일봉 또는 시간봉 기반으로 가정한다. 공매도·신용·선물·초단타는 확정된 요구사항이 아니며 별도 증거금·청산·포지션 모델이 필요하다. 지원 시장 세 종류를 설계에 모두 포함하되 실제 연결과 검증은 단계적으로 진행한다.

## 확인한 문제와 영향

### 1. 백테스트의 시간·보유·비용 정의

- core/backtester.py:211은 종가 t로 만든 비중을 t-1→t 수익률에 곱한다. 가격 100→110→99, lookback=1 모멘텀에서 비용 없이 +10%가 나온다. 관측 전 상승을 취하고 이후 하락을 피하는 계산이다.
- :200은 0을 미보유로 처리한다. 그러나 전략 함수는 0을 홀드로 설명한다. RSI·볼린저가 매수 이후 중립 구간에 진입하면 보유를 유지하지 못한다.
- :203의 최초 diff를 0으로 채워 최초 매수 비용이 누락된다. 평평한 가격에서 첫날 매수, 수수료 1%를 주어도 수익률은 0%다.
- :204는 자본 대비 거래금액이 아닌 종목별 0/1 변화에 비용을 곱한다. 현금에서 두 종목 동일가중 진입, 수수료 1% 조건에서 비용을 2%로 계산한다. 반대로 비중만 달라지는 거래는 비용을 놓칠 수 있다. 항상 일정 배수로 과대 계산된다고 일반화하면 안 된다.
- rebalance_period는 선언·전달만 되고 실행에서 읽히지 않는다. 동일 데이터에 1d와 1M을 주어도 결과가 같다.
- 목표 비중을 그대로 매일 수익률에 곱하면 보유 수량 고정과 다르다. 가격 변동에 따른 비중 변화를 추적해야 buy-and-hold 및 리밸런싱 비용을 정확히 계산할 수 있다.
- 월말 평가액 pct_change는 첫 달 수익을 누락한다. 한 달 이내 테스트의 월별 결과는 빈 배열이다.
- CAGR·샤프·소르티노가 모두 252를 사용한다. 달력 기간과 관측 주기를 분리해야 한다. 승률·손익비는 거래별 손익이 아닌 일별 수익으로 계산되어 의미도 명시해야 한다.
- 알 수 없는 전략 이름은 오류 대신 동일가중으로 실행된다. 자동 운용에서는 설정 오류를 조용히 매수로 변환하면 안 된다.

수정 원칙: t까지 확정된 데이터로 판단하고 다음 거래 가능한 봉의 시가 등 명시한 체결 규칙을 적용한다. 종가만으로 shift(1)을 넣는 것은 시간 정렬의 일부를 교정할 뿐 실제 다음 시가 체결을 재현하지 못한다. 분석용 수정가격과 실제 체결가격도 구분한다.

### 2. 시장별 데이터 계약 불일치

- 국장 get_tickers는 KOSPI 100개, KOSDAQ 50개를 순서대로 요청한다. 스크리너가 다시 앞 100개를 잘라 정상 응답 시 KOSDAQ 후보가 제외될 수 있다. 제한을 하나 지우는 것만으로 전체 시장 수집이 되지 않는다.
- 국장 sector에는 업종 대신 KOSPI/KOSDAQ가 들어간다. 현재 필드로 업종 중립화나 업종 비중 상한을 계산하면 안 된다.
- 국장 ROE는 PBR/PER×100 추정치이며 미장 ROE는 returnOnEquity를 변환 없이 사용한다. 값의 단위·실측/추정 여부가 계약에 없다. 화면의 퍼센트 임계값을 공통 적용할 수 없다.
- 미장 get_tickers에서 시가총액은 기본 0이고 스크리너도 이 값을 복사한다. 기본 시가총액 정렬의 의미가 사라진다.
- 코인 get_fundamental은 빈 값을 반환한다. 주식 PER·ROE 조건을 지원하는 것처럼 노출하면 전부 탈락한다. 가격·거래량 전략과 재무 팩터 전략의 지원 조건을 분리해야 한다.
- api/market_data.py:109는 분봉도 YYYY-MM-DD로 반환하여 하루 내 시각을 잃는다. 국장 프로바이더는 interval을 실제 조회·리샘플링에 반영하지 않는다.
- 코인 날짜 변환은 timezone 없는 datetime.timestamp()를 사용하고 반환 인덱스도 timezone 정보가 없다. 실행 PC 시간대에 따라 기간이 달라질 수 있다.
- 국장 yfinance 대체 경로는 접미사 없는 종목에 무조건 .KS를 붙인다. KOSDAQ는 종목 메타데이터로 구분해야 한다.
- close_prices.dropna()는 한 종목의 결측으로 전체 날짜를 제거한다. 신규 상장·거래정지·데이터 장애를 구분하지 못한다.

### 3. 자동 운용에 필수인 상태가 없음

계좌, 주문가능 현금, 주문 예약금, 미체결, 부분체결, 주문 취소, 재시도, 원장 대사, 실행 락이 없다. market 문자열만으로 계좌·거래소·통화·상품 종류를 표현할 수 없다. PaperTradeRequest.amount는 매수 금액인지 수량인지 불분명하다.

기존 price_cache는 DATE와 정수 volume으로 되어 있어 여러 봉 주기, 소수 거래량, 거래 장소를 정확히 저장하기 어렵다. portfolios에는 기준 통화와 연결 계좌가 없고 trades만으로 미체결 주문을 복구할 수 없다. 사용자 테이블의 RLS는 있으나 API 사용자 인증과 계좌 소유권 검증은 구현되어 있지 않다.

### 4. 실행·재현 환경

프론트엔드 npm run build는 통과했다. 큰 번들 경고가 있다. backend/venv/Scripts/python.exe는 참조하는 원본 Python311 실행 파일을 찾지 못해 시작하지 못했다. requirements.txt에는 코드가 직접 import하는 FinanceDataReader의 배포 패키지 finance-datareader가 없다. 깨끗한 환경 재현을 위해 Python 버전과 의존성을 정리해야 한다.

## 권장 아키텍처

```text
React 운영 화면 → FastAPI 제어 API → 저장된 전략/운용 설정
                                      ↓
거래 캘린더 → 독립 실행 워커 → 데이터 유효성 검사
                                      ↓
                         공통 전략 판단 → 목표 비중
                                      ↓
                     계좌별 자금 배분 → 위험 한도 검사
                                      ↓
                 실제 보유·미체결을 반영한 주문 차이 계산
                                      ↓
                    주문 의도 영속화 → 실행 어댑터
                                      ↓
             과거 체결 시뮬레이터 / 모의 브로커 / 실거래 브로커
                                      ↓
               체결 이벤트 → 현금·보유 원장 → 잔고 대사
                                      ↓
                          다음 실행에 상태 반영
```

핵심은 팩터 엔진 하나가 아니라 전략·계좌·주문·원장의 일관성이다. 팩터 점수와 기술적 지표는 전략이 소비하는 입력이다. 공통 Strategy 인터페이스로 기술적 전략, 횡단면 팩터 전략, 자산배분 전략을 모두 수용한다.

백테스트·모의투자·실거래는 동일 전략과 주문 계획·위험 검사 코드를 사용한다. 시계, 시장 데이터 공급, 체결 어댑터를 교체한다. 실거래 체결과 시뮬레이션의 차이는 남으므로 같은 코드 사용만으로 성과 일치가 보장되지는 않는다.

처음부터 마이크로서비스를 여러 개 만들 필요는 없다. Python 도메인 패키지 하나, API 프로세스, 별도 워커 프로세스, PostgreSQL로 시작한다. 워커는 브라우저가 닫혀도 동작해야 하고, 무인 운용 배포 환경에서는 프로세스 재시작과 상태 복구를 제공해야 한다.

국장·미장·코인의 차이는 어댑터와 규칙에 둔다. 거래일·휴장·세션·서머타임, 호가와 수량 단위, 주문 유형, 비용 시행일, 결제·매수 가능금액을 시장/계좌별로 관리한다. KRW와 USD는 각각 보관하고 통합 보고서만 시점별 환율로 환산한다. 코인 계좌의 현금을 주식 계좌가 바로 쓸 수 있다고 가정하지 않는다. 계좌간 이체·환전 자동화는 별도 범위다.

주문 의도에는 quantity와 quote_amount를 구분하며 상품과 주문 유형에 맞게 검증한다. 예를 들어 업비트 시장가 매수는 총액, 시장가 매도는 수량이다. [업비트 주문 생성 공식 문서](https://docs.upbit.com/kr/reference/new-order)

한국투자증권 공식 샘플에는 국내·해외 주식과 모의/실전 환경 구분이 있어 추후 연결 후보를 평가할 때 참고할 수 있다. 현재 사용자 선택으로 확정한 것은 아니며 실제 계좌의 API 권한·지원 주문·시장 범위는 연결 시 검증한다. [공식 샘플 저장소](https://github.com/koreainvestment/open-trading-api)

## 자동 실행의 정상·장애 처리

1. 계좌를 동기화한 후 전략의 실행 시각과 완성된 봉을 확인한다.
2. 전략 버전·판단 시점·계좌별 run_id를 생성하고 DB 유니크 제약 및 만료되는 실행 락으로 중복 워커를 제어한다.
3. 사용 가능한 과거 데이터만으로 목표를 생성하고 판단 근거와 데이터 버전을 저장한다.
4. 다른 전략의 배정·기존 미체결·예약금을 포함해 주문가능금액을 계산한다. 매도 접수만으로 현금이 들어왔다고 가정하지 않는다.
5. 주문 의도와 발송 대기 이벤트를 동일 트랜잭션에 기록한 다음 브로커에 전송한다.
6. 전송 타임아웃은 주문 실패와 다르다. UNKNOWN 상태로 두고 브로커 주문/체결을 조회해 확인한다. 확인 없이 새 주문을 반복 전송하지 않는다.
7. 부분체결은 체결 이벤트별로 원장에 반영하고, 취소 요청 뒤에도 최종 체결·취소 상태를 확인한다.
8. 재시작 시 전략 실행보다 잔고 대사와 미확정 주문 복구가 먼저다.

주문 상태 예: CREATED → SUBMITTING → ACKNOWLEDGED → PARTIALLY_FILLED → FILLED. REJECTED, CANCELED, EXPIRED 분기와 UNKNOWN, CANCEL_PENDING 상태를 별도 관리한다. 브로커 고유 상태는 어댑터에서 매핑한다.

run_id와 order_intent_id로 로컬 중복을 차단하되 DB 유니크 제약만으로 외부 주문의 exactly-once를 보장한다고 주장하지 않는다. 브로커의 사용자 지정 주문 ID 지원 여부와 조회 방법을 고려해야 한다. 업비트 identifier는 계정 내 고유하고 재사용할 수 없다. [공식 주문 ID 정책](https://docs.upbit.com/kr/reference/new-order)

중지 정책은 신규 주문 중지, 미체결 취소, 보유 청산을 구분한다. 데이터 장애 때 무조건 시장가 전량 청산하는 방식으로 설계하지 않는다. 손실 한도와 청산·재개 정책은 운용 설정에서 별도로 정한다.

## 필요한 저장 모델

- instruments / instrument_rules: 상장·폐지 이력, 거래 장소, 단위, 규칙 유효기간.
- bars / corporate_actions / fundamental_versions: 봉 주기·UTC 시각·출처, 기업행사, 공시·수집·정정 시각. 같은 회계기간 정정 공시를 덮어쓰지 않는다.
- strategy_versions / deployments / strategy_runs: 전략 불변 버전, 계좌 배정, 모드, 실행 상태, 데이터 버전, 실행 락.
- broker_accounts / account_cash / allocations: 계좌별 통화, 가용·예약·결제대기 금액, 전략 예산. API 비밀키 본문은 운용 기록에 저장하지 않는다.
- order_intents / orders / order_events / fills: 요청·브로커 주문·상태 이벤트·개별 체결 분리. 계좌와 브로커 기준 체결 ID 유니크.
- ledger_entries / positions / account_snapshots: 현금·수량 변화의 원본 기록과 조회용 잔고. 현재값만 덮어쓰는 방식으로 끝내지 않는다.
- reconciliation_runs / risk_events / worker_heartbeats / outbox: 차이·중지 근거·실행 생존 상태·재발송 가능한 이벤트.
- backtest_jobs / backtest_results: API 요청과 긴 계산 분리. 결과에 요청 기간/실제 기간, 제외 종목, 가정, 비용, 전략 버전 포함.

## 구현 순서와 완료 조건

| 단계 | 산출물 | 완료 기준 |
| --- | --- | --- |
| 1. 계산 기반 교정 | 재현 가능한 Python 환경, 입력 검증, 신호/보유 정의, 명시적 체결 시점, 수량·현금 기반 백테스트 | 최초 수수료, 미래 데이터 차단, 홀드 유지, 리밸런싱, 비용, 첫 달 수익을 고정 데이터로 검증 |
| 2. 공통 실행과 모의 원장 | Strategy/Broker 계약, 계좌 현금·예약금·주문·체결, 과거 시뮬레이터 | 한 전략이 세 시장의 합성 데이터에서 동일 계약으로 동작하고 초과 주문·중복 체결 차단 |
| 3. 지속 모의 운용 | 워커, 캘린더, 실행 락, 복구·대사, 운영 화면 | 브라우저 종료·프로세스 재시작·네트워크 실패 후 상태 복구, 중복 주문 없음 |
| 4. 시장별 데이터와 브로커 연결 | 사용자 선택 후 어댑터, 실제 규칙·데이터 검증 | 지원 시장별 시세·잔고·주문 상태·취소를 테스트/모의 환경에서 검증 |
| 5. 전략 검증 확대 | 시점 유니버스·재무 이력, 팩터 랭킹, 비용 민감도·기간 분리 검증 | 당시 알 수 없던 데이터 배제, 데이터 범위와 제외 사유 공개 |
| 6. 실운용 전환 | 시장별 제한된 배정, 모니터링·중지·복구 | 각 연결의 검증 통과와 사용자가 정한 운용 설정 확정 후 단계적 활성화 |

시점 재무 이력 수집은 병행할 수 있다. 가격 기반 전략의 모의 운용 골격을 만드는 데 모든 시장의 재무 DB 완성이 선행할 필요는 없다. 반면 과거 재무 팩터 전략의 성과를 주장하려면 해당 시점 데이터가 먼저 필요하다. 최적화는 실행·원장이 안정된 다음 추가하며 초기 비중 방식은 단순하게 유지한다.

필수 장애 검증: 주문 접수 직후 통신 끊김, 중복 체결 이벤트, 순서가 뒤바뀐 이벤트, 부분체결 직후 취소, 두 워커 동시 실행, 재기동, 오래된 시세, 거래정지, 환율 결측, 현금 부족, 시장별 휴장. 수익률 테스트와 별도로 이 시나리오를 통과해야 무인 운용을 평가할 수 있다.

## 검증 기록 및 이전 진단 정정

번들 Python의 numpy/pandas를 사용해 원본 backtester.py에서 AST로 클래스 정의만 추출해 실행했다. 외부 프로바이더 생성·네트워크·키 로드를 우회한 계산 단위 검증이므로 전체 백엔드 기동 검증과는 다르다.

| 재현 | 관측 |
| --- | --- |
| 100→110→99, 1일 모멘텀, 비용 0 | +10% |
| 평평한 가격, 첫날 매수, 수수료 1% | 0% (최초 비용 누락) |
| 100→100→110, 신호 1→0→0 | 0% (홀드를 미보유로 해석) |
| 두 종목 평평한 가격, 현금에서 동일가중 진입, 수수료 1% | -2% |
| 같은 데이터, 리밸런싱 1d 대 1M | 결과 동일 |
| 단일 월 데이터 | monthly_returns=[] |
| 잘못된 전략 이름 | equal_weight와 결과 동일 |
| frontend npm run build | 통과, 큰 번들 경고 |

이전 대화의 '스크리너에서 오늘 뽑은 종목이 자동으로 백테스터로 연결된다'는 단정은 현재 코드로 입증되지 않는다. BacktestPanel은 사용자가 입력한 symbols를 전달한다. 최신 선정 종목을 과거에 적용할 때 발생할 편향은 설계상 주의점으로 구분한다.

'shift()가 없다'는 검색만으로 모든 전략의 미래 정보 사용을 입증할 수는 없다. 이번에는 실제 계산식과 모멘텀 재현으로 확인했다. 항상 매수하는 전략까지 동일한 정보 편향을 갖는다고 일반화하지 않는다.

이전 문서의 특정 샤프 하락 폭·생존 편향의 수익률 왜곡 폭·개발 주수는 이번 검토에서 검증되지 않았다. 구축 일정과 수익 성과의 근거로 사용하지 않는다.
