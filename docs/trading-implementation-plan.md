# 자동 운용 구현 작업과 검증 기준

작성: 2026-09-12 · 구현 설계 완료 조건. 아래 체크박스는 구현 완료 표시가 아니다.

참조: [상세 설계](trading-system-design.md), [데이터·API 계약](trading-contracts.md)

## 1. 작업 순서

각 작업은 로컬에서 검증한 뒤 다음 단계로 진행한다. 시장별 브로커 선택을 기다려야 하는 작업은 T6뿐이다. T1~T5는 업체 미정 상태에서 수행 가능하다.

| ID | 작업 | 수정/추가 대상 | 선행 | 완료 산출물 |
| --- | --- | --- | --- | --- |
| T1 | 실행 환경과 회귀 기준 | requirements, 테스트 설정, README 실행법 | 없음 | 새 .venv에서 import·테스트 재현, 기존 config 보존 |
| T2 | 전략·체결·원장 계산 | domain, backtesting, core/backtester 호환 래퍼 | T1 | 시간 순서·현금·수량 기반 엔진과 기존 오류 회귀 검증 |
| T3 | 데이터 표준화 | ports/market_data, providers 래퍼, API 시각 응답 | T1 | 세 시장에 같은 데이터 계약·실패/범위 표시 |
| T4 | 영속 계좌·모의 주문 | migrations, persistence, application, paper broker | T2 | 실제 PostgreSQL 트랜잭션으로 중복·예약·체결 검증 |
| T5 | 상시 운용과 운영 화면 | workers, v1 API, React 운영 화면 | T3,T4 | 모의 전략 자동 실행·중지·복구를 UI와 무관하게 검증 |
| T6 | 시장별 브로커 | brokers/{selected}, 어댑터 계약 테스트 | T5, 업체 선택 | 공식 테스트/모의 또는 조회 환경으로 상태 매핑 검증 |
| T7 | 팩터와 연구 도구 | 시점 재무·유니버스, 팩터 전략, 결과 화면 | T2,T3 | 시점 데이터 가용성·기간 분리·비용 민감도 검증 |
| T8 | 지속 실운용 준비 | 호스트 감독, 모니터링, 백업/복원 절차 | T5,T6, 운용 설정 확정 | 모드·계좌 격리, 장애·복구 수용 기준 통과 |

T7은 기술적 전략의 모의 운용과 병행 가능하다. 모든 팩터 기능이 끝나야 주문 원장을 만들 수 있는 구조로 만들지 않는다. 달력과 데이터 정합성은 T5에 선행해야 한다.

## 2. T1~T2: 첫 구현 묶음

- [x] Python 지원 버전과 의존성, 개발용 pytest 설치 방법을 기록한다.
- [x] 직접 import 목록과 requirements를 대조하고 데이터 공급자 의존성을 분리한다.
- [x] 외부 키 없이 domain과 계산 모듈을 import할 수 있도록 프로바이더 생성을 분리한다.
- [x] StrategySpec을 검증하여 오타 전략, 음수 자금, 중복 종목, 잘못된 window를 거절한다.
- [x] NO_CHANGE/TARGET/BLOCKED와 목표 상태/실제 보유를 구현한다.
- [x] 종가 확정 이후 다음 적격 시가 체결, 최초 비용, 수량 내림, 현금 보존을 구현한다.
- [x] 목표 비중을 리밸런싱·신호 변경 때만 주문한다.
- [x] 월별 수익, 실제 기간 CAGR, 성과 지표를 계산한다.
- [x] v1 결과와 계좌 평가액을 분리해 UI에 표시한다.

이 묶음은 브로커 연결을 하지 않는다. 검증되지 않은 계산 엔진을 실주문에 연결할 수 없도록 paper/backtest만 구성한다.

## 3. 계산 수용 테스트

| ID | 입력/사건 | 반드시 확인할 결과 |
| --- | --- | --- |
| C01 | t 종가를 사용해 진입, 다음 거래 세션 존재 | t 종가 이전 수익 없음, 체결은 선택한 다음 시가 이벤트 |
| C02 | 이후 봉 가격을 바꾸어 동일 과거 구간 재실행 | 과거 Decision·주문 계획은 동일. 이후 실제 체결값만 달라질 수 있음 |
| C03 | 현금 1,000, 단가100, 수수료1%, 정수수량 | 최대9주, cash91, qty9, NAV991 |
| C04 | C03 이후 단가110, 거래 없음 | cash91, qty9, NAV1081. 자동 비중 조정 없음 |
| C05 | C03 수량 전부 단가110 매도, 수수료1% | 매도 수령980.10, 최종 cash1071.10, qty0, 실현손익71.10 |
| C06 | RSI 진입→중립→중립 | 목표 상태 유지, 원치 않는 청산 없음 |
| C07 | 동일 비중 2종목, 한쪽만 상승, 일정 전 | 보유 수량 고정, 종목 비중은 변동 |
| C08 | C07에서 월말 리밸런싱 | 다음 적격 시점에 실제 변경 수량만 거래·비용 부과 |
| C09 | 한 달 데이터의 평가액1000→1100, 외부 흐름0 | 첫 월 수익0.10, 빈 목록 아님 |
| C10 | 불명 전략/NaN/중복 종목/window 역전 | 명시적 입력 오류, 동일가중 대체 실행 없음 |
| C11 | 부족한 워밍업/거래정지/새 상장 | 사유가 기록되고 미래 값 보간으로 매매하지 않음 |
| C12 | 액면분할 2:1, 9주×100→18주×50 | NAV 변화 없음, cost_basis 일관 |
| C13 | 현금배당 이벤트와 수정가격 | 배당 수익 1회 반영 |
| C14 | 주식 휴장·미국 DST·코인 연속 봉 | 시장 캘린더별 판단/체결 시각 정확, 날짜만으로 합치지 않음 |
| C15 | 체결 가능한 미래 봉 없이 종료 | 새 주문은 만료/미체결, 마지막 종가 소급 체결 없음 |

미래 데이터 독립성은 Strategy가 받은 snapshot의 행만 검사하는 테스트로 끝내지 않는다. 전체 데이터셋의 이후 부분을 바꾸어도 앞선 결과가 같은지 통합적으로 검사한다.

## 4. 주문·원장·복구 수용 테스트

| ID | 장애/경쟁 | 반드시 확인할 결과 |
| --- | --- | --- |
| O01 | 두 워커가 같은 계좌·일정 실행 | run 하나, 동일 주문 의도 하나 |
| O02 | 한 주문에 동일 fill 두 번 수신 | quantity/cash/fee 모두 1회 변경 |
| O03 | 체결이 접수 응답보다 먼저 도착 | 주문 연결 후 반영, 체결 분실 없음 |
| O04 | 접수 성공, 응답 타임아웃 | UNKNOWN→조회 복구, 새 매수 중복 없음 |
| O05 | 조회 결과 불명 또는 브로커 장애 | UNKNOWN 유지·노출 증가 차단, 자동 실패 확정 없음 |
| O06 | 10개 주문→4개 체결→취소 | 4개 원장 반영, 잔여6개 예약은 취소 확정 후 해제 |
| O07 | 취소 요청 중 나머지6개 전량체결 | 최종10개 보유, FILLED. CANCELED로 손실 기록 없음 |
| O08 | 원장 commit 전후 프로세스 종료 | 재기동 후 journal 중복 없음, cursor 재조회 가능 |
| O09 | 리스 만료 후 옛 워커 재등장 | 오래된 token commit 거절, 불명 전송을 새 워커가 재전송하지 않음 |
| O10 | PAUSE와 발송 동시 실행 | 새 epoch 이후 계획 차단, 전송 중 주문은 추적하여 상태 표시 |
| O11 | 주문 예약이 브로커 가용액에도 반영 | 예약금 이중 차감 없음, 미확정 반영은 보류 |
| O12 | 외부 수동 주문·입금·출금 발생 | 근거 이벤트로 대사, 출처 불명 수량 자동 매도 없음 |
| O13 | 실체결 비용이 계획보다 큼 | 실제 fill 기록 보존, 위험 사건과 ATTENTION 처리 |
| O14 | 사용자가 타인 account_id로 주문 조회/명령 | 인증·소유권 거절, RLS 우회 경로 없음 |
| O15 | paper 계좌에 live adapter 요청 | 모드 불일치 거절, 실주문 호출0 |
| O16 | 동일 API 멱등키에 다른 body | 409, 기존 의도 변경 없음 |
| O17 | DB 백업 복원 후 worker 시작 | 조회·대사 우선, outbox 무조건 발송 없음 |
| O18 | 다일 중단 후 복구 | latest_only 정책, 밀린 과거 매매 몰아서 실행 없음 |

O01/O08/O09/O11은 실제 PostgreSQL에서 트랜잭션·락·유니크 제약을 검증한다. 메모리 mock만으로 원자성이 검증됐다고 표시하지 않는다. 외부 브로커 호출 경계는 장애 주입 가능한 가상 브로커로 먼저 검증한다.

## 5. 설계 검토에서 반영한 충돌 해결

| 잠재 충돌 | 설계 결정 | 확인 위치 |
| --- | --- | --- |
| 월간 리밸런싱과 일간 청산 신호 | 신호 변경 또는 일정에서 거래, 평소 수량 고정 | 상세 설계 §5 |
| 홀드0과 현금0 혼동 | NO_CHANGE와 TARGET={} 분리 | 상세 설계 §5 |
| DB 리스가 외부 주문도 보호한다는 가정 | 불명 접수 조회·복구, 리스만으로 exactly-once 주장 금지 | 계약 §7 |
| 취소 요청과 체결 경쟁 | lifecycle/resolution/cancel_state 분리 | 계약 §6 |
| 목표100% 투자와 비용 때문에 잔고 부족 | 수량 내림, 비용 여유, 실제 가용액으로 제한 | 상세 설계 §6 |
| 브로커 예약금과 로컬 예약금 중복 | local_pending/broker_managed 구분 | 계약 §5 |
| 브로커 실체결이 내부 한도 위반 | 사실 기록 후 중지, 체결 버리지 않음 | 계약 §5 |
| 동일 계좌 여러 전략 중복 청산 | v1 계좌당 deployment 하나, 후속 하위 원장 | 상세 설계 §1 |
| 수정주가와 배당 현금 중복 | 분석/체결 가격 분리, 기업행사 이벤트 | 상세 설계 §4,8 |
| 24시간 봉 경계의 불가능한 시가체결 | 지연 반영 후 적격 이벤트 선택 | 상세 설계 §8 |
| 포지션 금액에 종목 소수점 제약 적용 | 원본 Decimal 보존, 규칙별 주문 정밀도 | 계약 §3 |
| 과거 데이터 정정으로 결과 재현 불가 | 불변 snapshot·revision 참조 | 계약 §3,4 |

## 6. 설계로 결정한 것과 나중에 필요한 것

지금 확정한 구현 기준: 모듈 경계, 공통 타입, 전략 의미, 주문 상태, 계좌 격리, 중지 종류, 복구 흐름, API, 원자적 저장 범위, 수용 테스트.

업체 선택 뒤 확정할 항목: API 자격·계좌 권한, 실제 시세 라이선스/지연, 주문 종류·ID 지원, 호가·최소수량·시장 세션, 수수료·세금/결제 규칙. 어댑터 구현 시점에 공식 문서를 확인하고 버전/근거를 저장한다.

실운용 전에 사용자가 정할 항목: 시장별 배정 자금, 종목/손실 한도, 사용할 전략 버전, 운용 시간, 중지 이후 재개 정책. 이 정보가 없어도 모의 운용 골격 구현은 진행할 수 있다.

이번 설계의 완성은 동작 무결함이나 수익성을 의미하지 않는다. 구현 완료 판단은 위 테스트와 실제 연결 검증 증거에 따라 내린다.
